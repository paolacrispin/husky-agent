# 03 — Agent tools spec (LLM / deterministic code boundary)

## Principle

The interpretation stage runs on the **Pi agent harness** (`@earendil-works/pi-ai`),
which is provider-agnostic: the actual model answering a given instruction —
Anthropic, OpenAI, DeepSeek, Google, or any other provider Pi supports — is a
runtime configuration choice (`HUSKY_AGENT_MODEL=<provider>:<model>` in
`.env`), not something the application code hardcodes. Whichever model is
configured can only invoke the tools in this document, with exactly these
parameters, expressed as Pi's TypeBox `Tool` schemas. No parameter reaches
`packages/core` as free-form text; every one of them passes through the
tool's schema (both Pi's own validation via `validateToolCall` and a zod
re-validation in `packages/agent`, per `AGENTS.md`'s convention) before
touching the resolver.

Pi's completion call is never given a forced tool choice — the model can also
respond with plain text to ask for clarification instead of being forced to
emit a tool call — see "Ambiguity handling" below.

## Tools v1

### `transfer`
```json
{
  "name": "transfer",
  "description": "Transfer an amount of a token to a recipient",
  "parameters": {
    "type": "object",
    "properties": {
      "token": {
        "type": "string",
        "description": "Token symbol, e.g. 'USDC', 'HSK'"
      },
      "amount": {
        "type": "string",
        "description": "Amount in human-readable units, e.g. '10.5'"
      },
      "recipient": {
        "type": "string",
        "description": "Contact alias or a 0x address"
      }
    },
    "required": ["token", "amount", "recipient"]
  }
}
```

### `swap`
```json
{
  "name": "swap",
  "description": "Exchange an amount of one token for another via the AMM",
  "parameters": {
    "type": "object",
    "properties": {
      "tokenIn": {
        "type": "string",
        "description": "Input token symbol"
      },
      "tokenOut": {
        "type": "string",
        "description": "Output token symbol"
      },
      "amountIn": {
        "type": "string",
        "description": "Amount of the input token, in human-readable units"
      }
    },
    "required": ["tokenIn", "tokenOut", "amountIn"]
  }
}
```

There are no other tools in v1 (no explicit `approve` tool — insufficient allowance
during a swap is handled deterministically inside the swap flow; the LLM doesn't
need to know that step exists).

## Recipient resolution (`recipient`)

1. Look up `recipient` as an alias in `contacts.json` (case-insensitive).
2. If there's no match and the string matches the format of a 40-hex-char `0x`
   address, use it directly.
3. If neither applies: reject before reaching "build," returning a clear error to
   the user ("I don't recognize 'X' and it's not a valid address").

`contacts.json` format (lives in `packages/core`, not in the LLM):
```json
{
  "juan": "0x0000000000000000000000000000000000000001",
  "maria": "0x0000000000000000000000000000000000000002"
}
```

## Ambiguity handling

If the model can't confidently extract `token`, `amount`, or
`recipient`/`tokenOut` from the instruction, the tool must not be called with
an invented value. The system prompt instructs the model to respond in plain
natural language asking the user for clarification **instead of** emitting a
tool call when required information is missing — it must never emit a tool
call with a guessed or placeholder value. Ambiguity test cases to include:
"send something to Juan" (missing amount and token), "swap 10 tokens"
(missing which input/output token).

## What the LLM does NOT do (reminder)

- It doesn't compute slippage or `amountOutMin`.
- It doesn't decide gas.
- It doesn't see or generate the summary shown for approval (that summary is
  generated by `packages/core` from the already-built calldata, see
  `04-security-policy-spec.md`).
- It has no access to keys or to the signing module.

## `packages/agent` (Pi harness integration)

```ts
// packages/agent/src/tools.ts
import { Type, type Tool } from "@earendil-works/pi-ai";
import { z } from "zod";

export const TransferInput = z.object({
  token: z.string().min(1),
  amount: z.string().regex(/^\d+(\.\d+)?$/),
  recipient: z.string().min(1),
});

export const SwapInput = z.object({
  tokenIn: z.string().min(1),
  tokenOut: z.string().min(1),
  amountIn: z.string().regex(/^\d+(\.\d+)?$/),
});

export const TOOL_DEFINITIONS: Tool[] = [
  {
    name: "transfer",
    description: "Transfer an amount of a token to a recipient",
    parameters: Type.Object({
      token: Type.String({ description: "Token symbol, e.g. 'USDC', 'HSK'" }),
      amount: Type.String({ description: "Amount in human-readable units, e.g. '10.5'" }),
      recipient: Type.String({ description: "Contact alias or a 0x address" }),
    }),
  },
  {
    name: "swap",
    description: "Exchange an amount of one token for another via the AMM",
    parameters: Type.Object({
      tokenIn: Type.String({ description: "Input token symbol" }),
      tokenOut: Type.String({ description: "Output token symbol" }),
      amountIn: Type.String({ description: "Amount of the input token, in human-readable units" }),
    }),
  },
];
```

`packages/agent/src/interpret.ts` resolves `HUSKY_AGENT_MODEL` (format
`<provider>:<model>`, e.g. `deepseek:deepseek-v4-flash`) against Pi's builtin
provider/model catalog via `resolveModel()`, then calls
`Models.completeSimple(model, { systemPrompt, messages, tools })`. Two
failure modes are handled distinctly:

- A thrown error from Pi itself (network/transport failure) becomes an
  `InterpretError`.
- Pi reporting `stopReason: "error" | "aborted"` **in-band** (provider/auth
  failures surface this way, not as a throw) becomes an
  `InterpretationFailedError` (a subclass of `InterpretError`).

Either way, nothing falls back to a heuristic parser and no tool call is ever
invented locally — see "Open items" below. A returned `toolCall` is validated
with Pi's `validateToolCall` and then re-validated with the matching zod
schema (`TransferInput`/`SwapInput`) before it's returned to the caller: even
though Pi validates `parameters` against the TypeBox schema, `AGENTS.md`'s
convention requires an independent schema check in application code before
anything from the LLM touches the resolver.

## Conversation state (multi-turn clarification)

`interpret()` takes the full conversation so far (`Message[]`, this project's
own minimal `{ role, content }` shape), not a single string — internally it's
converted to Pi's own message format via `toPiMessages()`. `packages/cli`
owns the `Message[]` array for the duration of one operation:

- On `needsClarification`, the CLI appends the assistant's clarification text
  and the user's next reply to the array, then calls `interpret()` again with
  the full history — this is what lets the model recover "to juan" from turn
  1 when the user only supplies the missing amount/token in turn 2 (Scenario
  7 in `07-demo-script.md`).
- Once a tool call is returned (or the user cancels), the conversation is
  **cleared**. Each new operation starts from an empty `Message[]`. History does
  not persist across unrelated operations in the same CLI session — this bounds
  context growth and stops an old operation's details from leaking into a new,
  unrelated instruction's interpretation.
